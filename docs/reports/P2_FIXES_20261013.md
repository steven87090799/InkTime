## 修復細節與驗證

依子系統補上原因、位置、修法、回歸案例及未驗證內容。

### F25 設定快取競爭

原因：快取命中檢查與取值之間，其他執行緒可能 clear 同一 dict。修復：`inktime/app/repositories/settings.py` 以同一個 RLock 保護讀取、資料庫刷新與 invalidate；避免舊刷新在 invalidate 之後重新寫回。P1 的 fresh Batch 權限讀取仍直接查資料庫。

回歸：`tests/unit/test_settings_repository_governance.py` 控制 reader 暫停，交錯不同 key 的刷新或 invalidate，確認讀取結果一致且沒有 KeyError。本機只做語法、Ruff、Linux 目標 mypy 與文件 validator；並行行為交由 hosted CI，未執行 Gunicorn 壓測。

### F04／F13／F18／F22 Batch 費用與提交結果

原因：requested／served 模型估價不一致、未知成本在摘要中變成零、補價只更新 usage 而未釋放已對帳 reserve，以及 UI 將 aggregate response 當成單個成功 Batch。

修復位置：`inktime/app/services/batch_analysis.py` 的 receipt／import 使用同一 served model；`inktime/app/repositories/analysis_batches.py` 增加 ledger 成本摘要與冪等 terminal settlement；`repositories/providers.py` 補價後觸發結算。結算與 reserve 釋放在同一 DB transaction，只有 terminal、全部 item 已有可信費用且無漏件／未知結果／reconciliation error 時才釋放；重播不改 terminal 狀態。

`web/templates/analysis_batch_detail.html` 將未知金額及推估顯示為「費用待確認」，區分已知小計；`analysis_batches.html` 顯示已提交／已準備分片與每個詳情連結，不立即 reload 蓋掉結果，不自動重送。service 額外回傳 submission_status／not_submitted_batch_ids，保留原有欄位與 HTTP 201 的 aggregate 合約。斷線後明確提示先核對遠端，並恢复按鈕。

回歸：`tests/unit/test_batch_analysis_lifecycle.py` 涵蓋 served 未定價、明確零費用、actual 優先、補價後釋放、仍有 unknown／missing 不釋放、重複結算及停用後未提交分片；既有管理頁 fixture 配合成本完整性更新。本機 Python／Jinja 語法、Ruff、Linux mypy、diff 檢查通過。hosted CI 與瀏覽器操作待確認，沒有真實付費請求。item／cache 的既有非 nullable 儲存欄位仍相容，UI 以 usage ledger 判斷未知成本；無 migration。

### F10／F54 Fallback 快取與單張付費驗收

F10 原因：fallback 沿用 primary prompt contract，實際選中通道的行為 revision 不在 cache key。修復：`providers/router.py` 的 channel 保存 analysis_revision，`services/providers.py` 使用語意 revision，`services/analysis.py` 的 request fingerprint 納入實際選中通道 revision。操作／價格／密鑰輪替不改語意 revision；儲存的歷史分析格式與 frozen plan 不改寫。

F54 原因：測試台沿用 high_model、未傳目前字幕規則，也接受 stored validator 與額外付費 repair。修復：`services/scoring_lab.py` 注入正式 PhotoAnalysisService，重用 plan 的模型、路由、規則、字幕控制、prompt version、reasoning、像素上限與 512 token cap。回答先落費用紀錄，之後檢查完整性與 current validator；不自動追加 paid repair。bootstrap 同步依賴；舊 high_model 仍由正式 plan 的升級相容邏輯處理。

回歸：`tests/integration/test_ai_cache_singleflight.py` 真 cache 流程＋假 provider，primary 送出前失敗後使用 fallback，改 fallback 語意 revision 後重新取得回答；`tests/unit/test_scoring.py` 覆蓋 current／legacy 模型不同、字幕界線、舊 schema、length 終止與單次計費保留。移除已退休的測試台自動 repair 預期，保留斷線未知費用紀錄。本機 Ruff／Linux mypy／diff 通過；CI 待確認，沒有真模型或圖片上傳。F11 其餘 Level 3／benchmark 接續處理。

### F11／F23 模型診斷接受條件與重複 benchmark

原因：Level 3／benchmark 使用歷史 stored validator，修復回答缺少完整性 guard；default／advanced 的退休 controls 沒有改變 wire request。

修復：`services/provider_contracts.py`、`services/model_benchmark.py` 改用 current live validator 並檢查 repair finish reason／refusal，已收到的費用紀錄仍保留；不完整 repair 不再被判成成功。診斷結果加入 production_acceptance=false 與 contract_scope；benchmark Markdown 明示較大 token cap／額外 paid repair，正式單張接受條件由 F54 測試台提供。保留明確診斷用途的額外修復，不把診斷成功宣稱為正式分析驗收。

`model_benchmark.py` 的 advanced 現在傳受支援的 side_caption_custom_rules，完整 request 與 default 不同；相同 axis 去重。`scripts/benchmark_models.py` 預設只跑 default，advanced 留作明確選用比較。

回歸：`tests/unit/test_provider_contracts.py` 覆蓋歷史 schema 與截斷 repair；`tests/unit/test_model_benchmark.py` 比較兩個 profile 的真正 wire body 並確認重複 axis 去除。本機 Ruff／Linux mypy／diff 通過；CI 待確認，沒有執行 live benchmark、真模型品質或實際帳單驗收。

### F38／F62／F63 還原身分與 Release 保存

F38：`services/secret_recovery.py` 在 create／restore 前比對 DB 的 master-secret fingerprint，並驗證所有 ciphertext 可由 bundle key 解密；verify 同樣驗證內層一致性及重複 key，沿用 v1 加密格式。錯誤 target 在建立 safety copy／改寫 key 或 DB 前拒絕；transaction 失敗時只補償確實被替換的 key。無 fingerprint 的舊 DB 至少驗證既有 secrets；沒有任何身分／密文證據的舊空 DB 無法證明裝置憑證身分，仍需人工核對來源，未解除 startup identity guard。

F62：`services/release_coordinator.py` 新增 rollback，先核對正式狀態、profile、Manifest 和所有 payload；`services/rendering.py` 委派 coordinator，`api/rendering.py` 對無效 target 回 409。`domain/rendering/release.py` 以同步暫存檔原子替換 pointer。rollback 在 metadata guard 內保存 `.rollback-intent.json` 與舊 pointer snapshot，DB transaction 更新同 profile 正式狀態及 published_at 提交標記；失敗補償 pointer，已提交而尚未清除的意圖由 startup reconcile／下一次 publish 完成。未提交意圖恢復原 pointer；無效意圖保留待核對，避免盲目回復。沒有 migration，不改其他 profile／failed／staged／device-test 狀態。

F63：`domain/rendering/release.py` 的 discard 在共享 metadata guard 內使用 DeviceTestReleaseStore.reference_snapshot 引用安全機制。已引用或 snapshot 不完整時保留 payload／index，舊 owner 不撤銷新 owner assignment。

回歸：`tests/unit/test_secret_recovery.py` 全部使用 disposable DB／dummy key，涵蓋 matching、wrong source、wrong target、inner ciphertext／duplicate key；`tests/unit/test_releases.py` 涵蓋已引用、引用快照不完整與真正未引用；`tests/integration/test_release_recovery.py` 覆蓋 Manifest／Payload／profile／kind 拒絕、DB／pointer 故障補償、提交前後的重啟對帳與冪等性。Ruff、Linux mypy、語法／diff 通過；CI 待確認。沒有執行真 Recovery、刪除正式內容、硬體或 NAS 斷電試驗；filesystem／key durability 與多程序 lease 搶占仍待現場接受。

### F05／F06／F26／F53 設定、Session 與上傳契約

F05：`factory.py` 在 auth／CSRF 解析 multipart 之前，僅為 `rendering.upload_font` 設定 64 MiB 加 1 MiB overhead 的 request body 上限；保留串流自身 64 MiB gate 與字型解析，其他 endpoint 的全域上限不變。HTTP 回歸採縮小的容量界線，確認 multipart overhead 可通過而超過檔案上限仍 413；32–64 MiB 真有效字型、解碼峰值記憶體及 NAS 暫存用量仍未實測。

F06：`api/settings.py` 集中 runtime 套用函式，update／rollback／import 共用。`session_policy.py` 的 Flask adapter 在 cookie 解碼與 expiration 時 fresh 讀取共用 DB；不依賴單一程序的舊 config／cache。`platform.py` 安裝此介面，保留原 signing serializer 與 session cookie 合約。測試 30→5→rollback30→import5、兩個 Flask app 共用同 DB、6 分鐘 cookie 在 30／5 分鐘政策下的接受／拒絕；實際多 Gunicorn worker 與登入持續負載未測。

F26：`repositories/settings.py` 的 dependency 明確允許 local_with_manual_ai 或 automatic_ai；`settings.html` 支援 one_of，管理員不用開自動 AI 才能調整手動分析模型／預算。F53：中文原因經 percent UTF-8 編碼於 Header，API 依 encoding marker 解碼；保留既有 ASCII clients 合約，不寫入密鑰或原始模型回應。
